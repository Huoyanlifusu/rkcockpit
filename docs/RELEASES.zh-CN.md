# 版本与发布策略

[English](RELEASE.md)

本文档说明 rkcockpit 的版本管理、测试、发布和支持方式。

本策略表达的是项目规划，并非有保证的服务级别协议。相比遵循固定日程，
项目会优先保证发布质量。

## 版本规则

rkcockpit 在适用的情况下遵循语义化版本规范。

在公共接口和部署行为仍处于稳定阶段时，版本采用 `0.x.y` 系列：

- `0.MINOR.0`：向后兼容的新功能或重要改进
- `0.MINOR.PATCH`：向后兼容的缺陷修复和安全修复
- `1.0.0`：首个明确承诺公共接口稳定的版本

自 `1.0.0` 起：

- `MAJOR`：包含不兼容的 API、配置、存储、部署或行为变更
- `MINOR`：包含向后兼容的新功能
- `PATCH`：包含向后兼容的修复

预发布版本可以使用 `-alpha.N`、`-beta.N` 或 `-rc.N` 后缀。

## 发布节奏

版本是否发布取决于就绪状态，而非严格遵循固定日程。

- 补丁版本：在确认缺陷或安全问题后按需发布。
- 次版本：在形成一组完整且已就绪的变更后，目标约每 4–8 周发布一次。
- 主版本：仅在确有必要引入不兼容变更时发布。
- 发布候选版本：涉及重要的认证、存储、部署、传输或迁移变更时，应先发布候选版本。

以上节奏是目标，并非发布保证。

## 分支与标签

- `main` 包含稳定且可发布的代码。
- `dev` 是持续开发所使用的集成分支。
- 功能和修复分支通常应以 `dev` 为合并目标。
- 发布拉取请求用于将经过测试的变更从 `dev` 提升至 `main`。
- 发布标签采用 `vX.Y.Z` 格式，并从 `main` 创建。
- 每个稳定版本标签都应有对应的 GitHub Release。
- 热修复从 `main` 分支创建，并且必须合并回 `dev`。

标签应使用附注标签。在维护者签名配置保持一致的情况下，可以使用签名标签。

## 兼容性

每个版本都必须说明已测试的以下兼容范围：

- Python 版本
- 宿主操作系统
- SSH 和 ADB 传输
- 配置与持久化数据格式
- HTTP API 行为
- 支持的浏览器
- systemd 与反向代理部署

当前 CI 矩阵在 Ubuntu 上测试 Python 3.9–3.12。未被 CI 覆盖的平台，
除非另行验证，否则应注明为尽力支持。

任何必要的迁移操作都必须在发布说明中醒目标注。

## 支持策略

在 `0.x` 阶段：

- 最新次版本会获得缺陷修复和安全修复。
- 较早的次版本仅提供尽力支持。
- 预发布版本不提供长期支持保证。

项目可在 `1.0.0` 之后引入更长的维护周期。

## 发布要求

发布版本前必须满足以下要求：

1. 计划纳入的完整单元测试套件全部通过。
2. Python 和 JavaScript 语法检查通过。
3. 涉及路径、认证和部署等安全敏感功能的测试通过。
4. 英文和中文文档保持同步。
5. 升级与回滚行为已完成审查。
6. 发布提交已存在于 `main`。

## 发布说明

每个 GitHub Release 都应包含：

- 内容摘要
- 用户可感知的变更
- 破坏性变更
- 升级说明
- 回滚说明
- 安全修复
- 已知问题
- 已测试的平台和 Python 版本
- 迁移要求
- 与上一版本的完整对比链接

## 初始版本

项目应从 `0.x.y` 系列开始。只有在当前测试发现机制和 macOS 路径保护问题
已解决，或已明确记录为已知限制后，才应创建首个版本标签。
